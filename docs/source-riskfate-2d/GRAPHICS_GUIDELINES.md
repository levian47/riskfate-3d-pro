# Riskfate — правила створення графіки

> **Призначення:** єдиний робочий стандарт для концептів, спрайтів, тайлів, анімацій, спорядження та інтерфейсу Riskfate. Документ застосовується до нових ресурсів і доповнює [GAME_CONCEPT.md](GAME_CONCEPT.md) та [PLANNING_FOUNDATION.md](PLANNING_FOUNDATION.md).
>
> **Статуси:** **Затверджено** — обов'язковий принцип; **Тестується** — робоче значення, яке можна змінити після перевірки; **Відкрито** — параметр ще не визначено. Жодне тестове число не є остаточним нормативом.

## 1. Візуальний напрямок

**Затверджено:**
- **2D pixel art, затверджена перспектива C — майже зверху (high top-down):** світ, дахи й крони дерев показуються переважно зверху; фасади будівель невисокі, але читабельні. Це остаточно затверджений художній стандарт (05.11.2026), не попередній варіант B. Він не вимагає класичної ізометрії чи довільно заданого кута у градусах; технічні пропорції ще перевірятимуться в ігровій сцені.
- **Простота графічних об'єктів (затверджено 05.11.2026):** чіткі прості силуети, стримана щільність деталізації, мінімум мікротекстур та ефектів; можливість створювати й повторно використовувати ігрові тайли, спрайти й варіанти об'єктів без непропорційних трудовитрат. Простота не повинна погіршувати читабельність чи художній характер. Точні кількість кольорів і розміри кожного ресурсу не затверджені.
- **Одна узгоджена візуальна мова:** співмірний розмір художнього пікселя, палітра, контраст, освітлення та принципи тіней для персонажів, NPC, монстрів, оточення, тайлів, предметів і ефектів.
- **Атмосфера:** поєднання темного й класичного фентезі, не суцільно похмура палітра; зберігати виразні світлі й темні акценти.

**Затверджений візуальний еталон базового героя:** надісланий власником аркуш `Riskfate — Base Hero / Character Concept`: каштанове об'ємне волосся, синя туніка/жилет поверх білої сорочки, коричневий пояс із боковою сумкою, темні штани та коричневі чоботи; спрощений піксельний стиль, збільшена видимість верхньої частини голови і плечей завдяки високому ракурсу. На аркуші показано ракурси front/back/left/right. Зберігати цей дизайн як **візуальне джерело для подальших тестів**. Затвердження еталона не затверджує його фактичні піксельні розміри, точність ракурсів, готовність спрайт-листа чи анімацій.

**Порівняльний концепт:** пізніший згенерований аркуш `BASE HERO — REFERENCE SHEET` із чотирма більш фронтальними ракурсами. Він **не є еталоном**; використовувати лише для порівняння. Обидва зображення збережено в `assets_source/character_concepts/`: `base_hero_approved_reference_v1.jpg` — затверджений візуальний еталон; `base_hero_comparison_concept_v1.png` — порівняльний концепт.

**Технічні вимоги для нових ігрових ресурсів (потребують перевірки щодо середовища):** забезпечувати відповідність остаточно затвердженій перспективі C (майже зверху), перевіряти читабельність у цільовому масштабі, узгодженість силуетів у потрібних напрямках і коректність опорних точок/колізій. Для базового героя вже затверджено вісім окремих статичних напрямків `S, SE, E, NE, N, NW, W, SW` по 48×64 px. Початковий художній еталон містить лише чотири ракурси і не є повним ігровим атласом; його історичні характеристики не змінюють нові правила перспективи.

## 2. Масштаб і технічні розміри

**Затверджено:**
- Єдина система масштабу світу й пропорцій для всіх категорій ресурсів. Об'єкти різних видів **не повинні** мати однакових габаритів, але повинні виглядати узгоджено поруч.
- Розрізняти **габарит видимого персонажа**, **розмір полотна кадру**, **точку опори**, **фізичну колізію** та **розмір тайла**: це різні параметри.
- Не розтягувати окремі ресурси довільно для виправлення відмінностей масштабу; готувати їх до узгодженого цільового розміру.

### 2.1. Єдиний масштаб від концепту до готової сцени (погоджено й уточнено 06.11.2026)

- **Два рівні підготовки:** загальний концепт локації — спрощена композиція для перевірки перспективи C, розміщення, масштабу й читабельності; виробничий референс окремого об'єкта — якісне стилізоване 2D-зображення з чіткою геометрією та контрольованою деталізацією, придатне для подальшого виготовлення pixel art. Концепт і референс не є готовими спрайтами.
- **Спільні пропорції та висоти:** той самий об'єкт у загальному концепті, окремому референсі та контрольній композиції має зберігати однакові *пропорції й визначену відносну висоту щодо еталонного героя*; не змінювати висоту, ширину, ракурс або конструкцію лише через перехід до детальнішого зображення. При зміні масштабу всього зображення застосовувати один коефіцієнт до об'єкта й героя. Не плутати фізичну/ігрову висоту об'єкта з висотою його зображення в пікселях або проєкцією на екран.
- **Герой задає масштаб:** базовий герой є сталою опорною величиною для всіх елементів оточення. Позначати його видиму висоту від верхівки волосся до підошов як **H** у контрольному напрямку S та погодженій перспективі C. Для кожного об'єкта фіксувати ширину й видиму проєкційну висоту відносно H; ці співвідношення переносити через весь процес «концепт → виробничий референс → ігровий спрайт → готова сцена». Це відношення видимих габаритів у погодженій проєкції, а не автоматичне визначення фізичних метрів. Стабільний масштаб базового героя не забороняє обґрунтованих відмінностей інших істот.
- **Як трактувати зміну відносного масштабу:** доручення зробити героя більшим щодо оточення означає залишити стандарт героя сталим і зменшити масштаб оточення. Наприклад, «герой ×1,25 щодо світу» відповідає зменшенню габаритів оточення до 1/1,25 = 0,8 за незмінного H. Застосовувати це правило до подальших правок; воно не скасовує явно погоджених винятків попередніх редакцій. Масштабування всього зображення разом із героєм змінює лише показ, але не співвідношення героя та світу.
- **Висота у світі та роздільність:** однаковий стандарт означає однакову нормалізовану висоту героя й ті самі пропорції об'єктів після приведення до спільного H. Файли різної роздільності, окремі великі референси, zoom камери та фізичні екрани можуть показувати різну кількість пікселів. В одному контрольному масштабі герой повинен мати однакову видиму висоту; не змінювати його пропорції чи масштаб відносно світу через перехід між етапами. Під час растрування враховувати дискретність піксельної сітки й перевіряти відхилення, а не довільно розтягувати спрайт.
- **Еталон для концептів і виробничих 2D-референсів:** вставляти актуальний затверджений непіксельний майстер [base_hero_2d_approved_reference_v1.png](assets_source/character_concepts/base_hero_2d_approved_reference_v1.png) зі збереженням його дизайну й пропорцій. Не підміняти його піксельним героєм і не вважати незалежне перемальовування генератором точним перенесенням майстра.
- **Еталон для ігрових перевірок:** використовувати фактичний затверджений піксельний кадр героя з репозиторію. **48×64 px — полотно кадру**, а видимий силует у перевіреному наборі v1 має висоту близько 58 px; не прирівнювати полотно до видимої висоти H. Порівнювати 2D-майстер і піксельний кадр після приведення їхніх видимих силуетів до спільного H. Остаточне числове значення масштабу світу цим правилом не встановлюється.
- **Поточний орієнтир композиції:** 06.11.2026 власник тимчасово залишив третій показаний варіант із гладким 2D-героєм як орієнтир його висоти. Пізніше того самого дня власник прямо доручив зберегти саме цей третій варіант як єдиний головний концепт у GitHub; оригінал збережено за стабільним шляхом RF-GRAPHICS-005 нижче. Це не затверджує автоматично всі пропорції оточення, точність перенесення майстра чи готовність ігрових спрайтів. До приймання сцени потрібні виміряні співвідношення об'єктів відносно H; поки вони не погоджені, значення залишаються тестовими.
- **Одне майстер-джерело:** отримувати чистий референс об'єкта без героя та його контрольне зображення з героєм з однієї геометрії, а не генерувати незалежно два різні варіанти. Для концепту локації застосовувати узгоджені пропорції тих самих об'єктів; якщо генерація їх спотворює, виправляти до приймання.
- **Єдина візуальна мова:** перевіряти поруч із героєм не лише розмір, але й візуальну вагу контурів, контраст, щільність деталей і характер майбутніх піксельних сходинок. Не допускати надмірно масивної темної обводки дерева чи споруди поруч із делікатнішим контуром героя. Однакова стилістика не означає однакової числової товщини контуру для всіх об'єктів.
- **Статус технології:** новий порядок «простий концепт → якісний непіксельний виробничий референс → окреме виготовлення pixel art → спільний тест у Godot» погоджений як напрямок перевірки, але його ефективність у серійному виробництві **не підтверджена**. Чинні затверджені оригінали й художня перспектива не змінюються.

## 3. Піксельна сітка, фільтрація та масштабування

**Затверджено:**
- Для ігрового pixel art застосовувати **nearest-neighbor**; не використовувати bilinear/trilinear-фільтрацію для персонажів, тайлів та інших піксельних ресурсів.
- Під час збільшення віддавати перевагу **цілочисельним масштабам** (×2, ×3, ×4 тощо); уникати довільних дробових масштабів **окремих** спрайтів.
- Не змішувати ресурси з різною візуальною щільністю пікселів: наприклад, дуже детальний герой поруч із грубо намальованим NPC.
- Не приховувати проблеми якості простим зменшенням великого концепту до низької роздільності: перед прийманням перевіряти контури, кольорові переходи та читабельність.

**Відкрито для повноцінного клієнта MMORPG:** остаточна базова роздільність вікна, zoom камери, налаштування stretch/content scale, обробка дисплеїв різних форматів і масштабування UI. Параметри чинного прототипу вже реалізовані й описані в [README.md](README.md); вони не стають остаточними стандартами всієї гри. Цілочисельне масштабування графіки не означає, що для всіх фізичних роздільностей екрана можна без компромісів отримати ідеальну картинку; це перевіряється окремо.

### 3.1. Геометрична якість і коригування піксельних спрайтів

**Затверджений принцип власника від 05.11.2026:** готовий ігровий спрайт має бути геометрично цілісним, читабельним і гармонійним на цільовій піксельній сітці. Під час підготовки дозволено коригувати вихідну геометрію для виправлення дефектів генерації; буквальна відповідність кожному випадковому пікселю концепту не є вимогою. Це стосується **всіх** типів ресурсів — будівель, природних об'єктів, предметів, персонажів і тайлів, а не лише дахів.

**Що перевіряти й виправляти:**

1. **Силует і форма.** Контур має переконливо передавати задуманий об'єкт без випадкових виступів, провалів, зайвих одиночних пікселів чи зламаних кутів. Дозволено локально уточнювати вершини, нахили, радіуси й співвідношення ділянок, якщо це покращує форму без зміни її характеру.
2. **Закономірний ритм сходинок.** Для прямих і похилих конструктивних країв довжини горизонтальних та вертикальних відрізків мають відповідати обраному нахилу. **Не потрібно робити всі сходинки однаковими:** коректна лінія може закономірно чергувати різні кроки. У паралельних країв перевіряти узгодженість напрямку та товщини; у кривих — плавну, обґрунтовану зміну кроків, без випадкових зламів.
3. **Узгодженість усередині об'єкта.** Зовнішній контур, обводка, межі кольорових площин, дахові шви, кладка, вікна, двері, гілки та інші деталі повинні підпорядковуватися одній геометрії й перспективі. Уникати випадкової зміни товщини ліній, нерівномірних відступів, помилкових перетинів, обірваних деталей і візуальних «дір».
4. **Симетрія та органічність за задумом.** У геометрично симетричних конструкцій (наприклад, відповідних схилів одного даху) перевіряти співмірність сторін та ритм країв. Водночас не нав'язувати симетрію деревам, каменям, рослинам, руїнам або задумано нерівним деталям. Природна асиметрія допустима; випадковий піксельний шум — ні.
5. **Узгодження з іншими ресурсами.** Перевіряти масштаб, художню щільність пікселів, палітру, освітлення, точки опори й стики з іншими об'єктами. Для тайлів окремо перевіряти шви й повторювані межі; для складених спрайтів — стики частин і шарів.
6. **Чиста піксельна техніка.** Виправляти форму безпосередньо на цільовій логічній сітці цілими пікселями. Не маскувати дефекти bilinear-згладжуванням, розмиттям, дробовим масштабуванням, автоматичним зменшенням великої ілюстрації чи довільним додаванням текстур. Зберігати коректну прозорість і відсутність сторонніх пікселів.

**Межі корекції:** дозволені локальні зміни геометрії робочого спрайта заради якості, але потрібно зберегти впізнаваність, загальний силует, задуману конструкцію, пропорції, масштаб щодо героя й затверджену перспективу C. Зміна художнього стилю, типу конструкції, ракурсу або істотна перебудова форми виходить за межі технічного очищення та потребує окремого погодження.

**Цілісна обробка об'єкта (підтверджено власником 05.11.2026):** від першої підготовки та після кожного виправлення перевіряти весь спрайт, а не лише ділянку, на яку вказав власник. Узгоджувати колір і візуальну товщину зовнішньої обводки, внутрішні лінії, кути та стики по всьому об'єкту; локальна правка не повинна порушувати його загальну гармонійність.

**Обов'язкова візуальна перевірка:** оцінювати готовий спрайт при **1×** поряд із героєм та іншими еталонними ресурсами; окремо збільшувати його в ціле число разів із **Nearest** для перевірки сходинок, контурів, симетрії там, де вона потрібна, внутрішніх ліній і випадкових пікселів. Автоматична перевірка розміру, формату PNG чи кількості кольорів **не замінює художню оцінку геометрії**.

**Збереження й приймання:** правити лише робочу похідну версію в межах дорученого виготовлення ресурсу. Незмінні вихідні концепти та затверджені оригінали не перезаписувати без окремого дозволу. Виправлений ресурс показувати власнику для візуального приймання; саме застосування цього правила не означає автоматичного затвердження результату.

### Метод підготовки піксельних спрайтів (RF-GRAPHICS-001)

**Затверджено як робочий процес** після позитивного оцінювання власником тесту від 04.11.2026. Це **метод підготовки**, а не автоматичне затвердження кожного результату як фінального ігрового ресурсу.

1. **Еталон і ракурси.** Взяти затверджений графічний еталон із GitHub; задати потрібні напрямки, зовнішність, спільний масштаб і палітру. Для тестового гуманоїда використано порядок `S, SE, E, NE, N, NW, W, SW` — усі вісім напрямків мають бути окремими, без підміни дублікатами.
2. **Концепт → справжня піксельна сітка.** Генероване велике зображення вважати лише вихідним матеріалом. Виділити персонажа для кожного ракурсу, привести до **цільової логічної сітки** з nearest-neighbor і, якщо потрібно, вручну доробити силует/деталі. Саме масштабування ×8 або зменшення великого арту **не створює** справжнього pixel art, якщо вихідна структура неправильна.
3. **Спрощення кольорів.** Застосовувати спільну контрольовану палітру без dithering і плавних градієнтів. Для тесту RF-GRAPHICS-001 використано **до 32 кольорів на весь набір** (27–30 непрозорих кольорів у конкретних кадрах). Кількість кольорів — **приклад успішного тесту**, не універсальна вимога до всіх істот і об'єктів.
4. **Чисті PNG.** Фінальні кадри — PNG RGBA зі справжньою прозорістю, без шахового фону й напівпрозорих контурів (для цього тесту значення alpha лише 0/255). Видаляти випадкові сторонні пікселі та не обрізати силует.
5. **Нормалізація кадрів.** Єдине полотно, масштаб, висота і точка опори для всіх ракурсів. Для цього тесту: **48×64 px** на кадр; видима висота близько **58 px**; спільна точка прив'язки **(24, 62)**; видимий персонаж 31–33 px завширшки. Це параметри **конкретного тесту**, не незмінний стандарт для всіх графічних ресурсів.
6. **Атлас лише з перевірених PNG.** Програмно компонувати кадри без повторного ресемплінгу. Для восьми тестових кадрів в одному рядку отримано атлас **384×64 px**. Перевіряти, що кожен сегмент атласу побітово відповідає окремому PNG.
7. **Контрольний перегляд.** Створювати окремий підписаний аркуш зі збільшенням **×8 через nearest-neighbor**; кожен логічний піксель має відображатися одноколірним блоком 8×8. Шаховий фон дозволений лише у прев'ю, не в ігрових PNG.
8. **Приймання.** Програмно перевіряти розміри, альфа-канал, палітру, відсутність обрізання, сторонніх пікселів і дублікатів, відповідність кадрів атласу; **окремо візуально** оцінювати напрямки, анатомію, зачіску, одяг і положення сумки. Автоматична перевірка не доводить правильність ракурсів чи художньої узгодженості. Після схвалення зовнішності потрібен тест у Godot.
9. **Звіт.** Для кожного файлу вказувати точну роздільність, формат, байти та КБ (1 КБ = 1000 байтів), результати перевірки й відомі обмеження. Розрізняти **довжину PNG-файлу** й фактично зайняте місце на файловій системі, яке залежить від розміру блоків.

Перед збереженням у репозиторій повторно перевірено CRC архіву, розміри кадрів, RGBA, alpha 0/255 та побітову відповідність сегментів атласу окремим PNG.
